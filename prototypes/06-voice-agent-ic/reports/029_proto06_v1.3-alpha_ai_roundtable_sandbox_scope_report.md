# 029 - Prototype 06 V1.3-alpha - Cadrage AI roundtable sandbox

Date: 2026-07-03

## Resume executif

Prototype 06 V1.3-alpha est defini comme une branche experimentale de Proto06, heritee de V1.2.3.

Son objectif est d'explorer un bac a sable IA admin-only pour tester des tours de parole generatifs entre Clara, Marco et Ana, sans modifier le parcours etudiant stable valide entre IC-Hub V0.9.9 et Proto06 V1.2.3.

V1.3-alpha n'est pas un nouveau projet et n'est pas un prototype independant. C'est une piste d'evolution de Proto06, separee du flux publie et scenarise.

## Base heritee

V1.3-alpha herite de :

- Proto06 V1.2.3 ;
- la logique de table ronde plurilingue ;
- les personnages Clara, Marco et Ana ;
- le manifest `climate-roundtable-demo` ;
- les badges pedagogiques et de securite ;
- le runtime scenarise comme fallback ;
- le chargement possible depuis IC-Hub ;
- les traces sobres ;
- le principe de non-impact sur le flux etudiant valide.

Le flux stable conserve reste :

```txt
IC-Hub V0.9.9
-> assignation Proto06
-> index-1.2.3.html
-> activitySource=hub-manifest
-> manifestId=climate-roundtable-demo
-> table ronde scenarisee
-> traces sobres
```

## Principe V1.3-alpha

V1.3-alpha peut explorer une table ronde IA plus libre, mais seulement dans un mode explicite :

```txt
admin-only
sandbox
experimental
non publie
non assigne aux etudiants
non relie automatiquement aux runs apprenants
```

Le bac a sable doit etre pense comme un espace de conception, pas comme un espace d'apprentissage.

Son usage attendu :

```txt
Admin / concepteur pedagogique
-> selection d'un contexte ou manifest de depart
-> generation experimentale de tours de parole
-> observation / comparaison / ajustement
-> eventuelle transformation ulterieure en contenu relu
-> publication separee dans un manifest stable
```

## Separation avec le parcours etudiant

La separation est le garde-fou central.

Le parcours etudiant stable ne doit pas :

- lancer V1.3-alpha automatiquement ;
- appeler une IA generative ;
- recevoir des tours de parole non relus ;
- dependre d'un provider IA ;
- stocker des brouillons ou reponses generatives dans `run_events` ;
- confondre activite publiee et experimentation sandbox.

V1.3-alpha doit donc etre expose, si elle est implementee plus tard, par une entree separee et lisiblement experimentale.

Exemples de formulations attendues :

```txt
Sandbox IA - admin seulement
Version experimentale non publiee
Ne pas assigner aux etudiants
Generation IA active uniquement dans cet espace
```

## Role du runtime scenarise

Le runtime scenarise reste le fallback obligatoire.

Si une generation IA echoue, si aucun provider n'est configure, si un garde-fou bloque la generation, ou si le mode sandbox est desactive, Proto06 doit pouvoir revenir a :

```txt
manifest publie
ou scenario local
ou tours de parole scenarises
```

Le fallback scenarise protege :

- la continuite pedagogique ;
- la reproductibilite ;
- la demonstration locale ;
- la separation avec le flux etudiant valide.

## Perimetre fonctionnel envisage

Une future implementation V1.3-alpha pourrait contenir :

- une page admin ou sandbox dediee ;
- un indicateur visuel permanent `V1.3-alpha` ;
- une selection de personnages Clara / Marco / Ana ;
- une consigne ou question commune de depart ;
- un contexte climatique de depart ;
- une generation de proposition de tour de parole ;
- une comparaison avec les tours scenarises ;
- un bouton d'export local ou brouillon, sans publication directe ;
- une indication claire du provider et du cout potentiel ;
- un journal local de diagnostic non sensible.

Ces elements restent des pistes de cadrage, pas une implementation dans cette mission.

## Hors perimetre V1.3-alpha

V1.3-alpha ne doit pas :

- remplacer Proto06 V1.2.3 ;
- modifier les anciens fichiers V1.2.x ;
- modifier IC-Hub V0.9.9 ;
- modifier le flux etudiant valide ;
- publier automatiquement un manifest ;
- assigner automatiquement une activite generative a un cours ;
- envoyer du texte apprenant a OpenAI ;
- exposer `OPENAI_API_KEY` ;
- appeler OpenAI depuis le navigateur ;
- stocker des generations IA dans `run_events` apprenants ;
- devenir un nouveau prototype independant ;
- contourner la revue humaine.

## Garde-fous IA requis

Toute future implementation doit respecter les garde-fous suivants :

- appels IA uniquement cote serveur ;
- aucun secret dans le navigateur ;
- aucun affichage de `.env` ;
- aucun log de cle API ;
- mode admin-only ;
- aucune activation dans le parcours student ;
- generation marquee comme experimentale ;
- sortie IA jamais consideree comme publiee par defaut ;
- revue humaine requise avant publication ;
- traces apprenantes sobres et separees des brouillons sandbox ;
- possibilite de desactiver le sandbox sans casser Proto06 stable.

## Relation avec le manifest `climate-roundtable-demo`

Le manifest existant peut servir de reference de depart :

- personnages ;
- langues ;
- theme climatique ;
- consigne ;
- question commune ;
- structure de table ronde ;
- tours scenarises humains comme point de comparaison.

Mais le manifest publie ne doit pas etre modifie directement par le sandbox.

Une sortie IA eventuelle doit rester un brouillon experimental jusqu'a revue humaine et publication explicite dans un nouveau manifest ou une nouvelle version de manifest.

## Relation avec les traces

Les traces apprenantes restent sobres.

Le sandbox IA peut avoir un journal de diagnostic separe, mais il ne doit pas polluer :

- les runs etudiants ;
- les `run_events` de parcours stable ;
- les manifests publies ;
- les exports pedagogiques valides.

Si un journal sandbox est ajoute plus tard, il devra separer clairement :

```txt
trace de conception
trace de generation
trace apprenante
```

## Architecture conceptuelle

```txt
Proto06 V1.2.3 stable
  |
  |-- Flux etudiant publie
  |     Hub assignment
  |     manifest publie
  |     runtime scenarise
  |     traces sobres
  |
  |-- V1.3-alpha sandbox
        admin-only
        generation experimentale
        brouillons non publies
        fallback scenarise
        aucune assignation etudiante directe
```

## Proposition de nommage futur

Si une implementation est decidee, les fichiers pourraient suivre un nommage explicite :

```txt
admin-1.3-alpha.html
admin-1.3-alpha.css
admin-1.3-alpha.js
script-1.3-alpha.js
style-1.3-alpha.css
```

Ou, si l'experimentation doit rester totalement separee de l'interface apprenante :

```txt
sandbox-1.3-alpha.html
sandbox-1.3-alpha.css
sandbox-1.3-alpha.js
```

Le second nommage est preferable pour eviter toute confusion avec le parcours etudiant.

## Definition de pret avant implementation

Avant de coder V1.3-alpha, il faudra decider :

- quel endpoint serveur IA serait utilise ou cree ;
- quel role exact peut acceder au sandbox ;
- quelles donnees peuvent etre envoyees au provider IA ;
- quelle forme prend le brouillon IA ;
- comment empecher toute publication directe ;
- comment afficher les couts et risques ;
- comment conserver le fallback scenarise ;
- comment verifier qu'aucune donnee apprenante n'est transmise.

## Recommandation

V1.3-alpha est une direction pertinente, a condition de rester un bac a sable admin-only strictement separe.

La prochaine mission utile serait une passe de specification plus operationnelle, sans code, listant :

- ecrans du sandbox ;
- donnees d'entree autorisees ;
- donnees interdites ;
- schema de brouillon IA ;
- garde-fous d'interface ;
- tests de securite attendus.

Seulement apres cette specification, une implementation limitee pourrait etre creee, sans modifier Proto06 V1.2.3 ni le flux Hub V0.9.9 valide.
