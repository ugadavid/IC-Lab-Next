Constat :

- le backend Proto06 expose `GET /api/health` et `/api/activities` ;
- il ne lit pas de header `Authorization` ;
- il ne connait pas les sessions Hub ;
- il ne sait pas identifier `admin`, `teacher` ou `student` ;
- il n'existe donc pas de role local exploitable pour proteger une generation IA.

Le backend Hub possede bien une auth par session et role, mais cette mission ne devait pas modifier IC-Hub. Aucun pont d'auth Hub -> Proto06 n'a donc ete cree.

## Endpoint ajoute ou limite documentee

Decision : option B.

Aucun endpoint `GET /api/sandbox/access` n'a ete ajoute, car le backend Proto06 ne peut pas verifier un role de maniere fiable.

Raison :

```txt
Pas d'auth reelle -> pas de fausse autorisation.
```

Limite documentee :

- un futur provider IA ne devra pas etre branche tant qu'un pont d'auth admin-only n'existe pas ;
- ce pont devra probablement passer par IC-Hub ou par un endpoint serveur capable de verifier un token Hub sans exposer le token dans l'interface.

## Recommandation suivante

Avant tout branchement provider, creer une mission separee pour un vrai pont d'auth admin-only.

Option prudente :

```txt
IC-Hub admin session
-> endpoint Hub admin-only
-> token court sandbox ou verification serveur
-> Proto06 sandbox lit uniquement un statut d'acces
-> bouton generation encore desactive jusqu'a validation
```

Une generation IA ne devra etre envisagee qu'apres validation de :

- refus teacher/student ;
- absence de secret dans le DOM ;
- absence d'appel OpenAI navigateur ;
- `store:false` cote serveur ;
- aucun stockage dans les runs apprenants.
